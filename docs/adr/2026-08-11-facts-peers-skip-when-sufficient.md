# 2026-08-11. Skip regenerating facts/peers/description once a company profile already exists

## Context

Following the same-day split of the asset-brief synthesis into a fast `news_summaries` call
and a deeper `key_issues`/facts/peers/description call (see the `_land_news_summaries`/
`_land_analysis` architecture introduced earlier this session), the owner observed that
`facts` (CEO, sector, industry, employees, exchange, country) and `peers` (comparable
companies) were still being regenerated by the LLM on every single refresh — even though
this data changes on the order of weeks or months, unlike `key_issues` (today's bull/bear
thesis) and `portfolio_impact` (today's P&L read), which genuinely need to stay current every
time. The owner's framing: *"do we always need to regenerate peers and key facts? … in case
it's already have data, can we not let it affect the key insights? so that in case it's slow,
we don't keep showing progress that make users feel it's slow."*

Because facts/peers/description shared ONE LLM call with key_issues, the time-sensitive part
of the refresh was paying for (and, on a slow model/provider, effectively gated behind) work
that most refreshes didn't need to redo at all.

## Decision

We will split `key_issues` + `portfolio_impact` (time-sensitive, always regenerated) from
`facts` + `peers` + `description` (slow-changing company profile) into two separate LLM
calls — `_synthesize_asset` (kept name, now key_issues-only) and the new
`_synthesize_facts_peers`. `_land_analysis` runs both CONCURRENTLY via `asyncio.gather`, but
the facts_peers call is gated by `_facts_peers_sufficient(prior)`: when the prior brief
already has a non-trivial `facts` value, a non-empty `peers` list, AND a `description`, the
facts_peers call is skipped entirely — zero LLM cost, zero latency contribution — and those
three fields carry forward from `prior` byte-identical via the existing non-regression merge.
This gate applies regardless of `force` (an explicit Refresh tap means "get me the latest
news", not "re-verify the CEO's name"). Live peer PRICES still refresh every time via
`_enrich_peers`, independent of whether the peer NAME/ticker set itself was regenerated.

## Consequences

### Positive
- The common case — refreshing an asset that's already been synthesized before — drops an
  entire LLM round-trip from the refresh's critical path, on top of the earlier news_summaries
  split. The time-sensitive key_issues call is never blocked by profile work it didn't need.
- Facts/peers/description are still generated correctly for a brand-new asset (empty prior),
  or if a prior synthesis genuinely came back thin (no `peers`, e.g.).

### Negative
- No staleness/refresh window: once a profile is judged "sufficient," it is NEVER
  regenerated again by this path, even months later. A genuine change (new CEO, a peer set
  that's gone stale) will not self-correct without a forced code path or a manual mechanism —
  none exists yet. Accepted as a reasonable trade-off given how rarely this data changes and
  the owner's explicit ask to stop paying for it by default; flagged as a known gap, not
  silently ignored.
- Sufficiency is a blunt presence check (any of ceo/sector/industry/employees, plus non-empty
  peers and description), not a quality check — a thin-but-technically-present profile from an
  earlier weak synthesis will never be topped up automatically.

### Follow-ups
- If stale profiles turn out to matter in practice, add an explicit periodic/manual
  "regenerate company profile" path (e.g., a settings action or a long time-based window)
  rather than silently reintroducing per-refresh regeneration.

## Alternatives considered

- **Keep facts/peers/description in the same call as key_issues, just tell the model to skip
  them when already known** — rejected: still pays for the full round-trip's base latency and
  doesn't remove an entire LLM call from the critical path, which is what was actually slow.
- **Time-based staleness window (e.g., regenerate every 30 days) instead of a pure
  presence check** — rejected for now as unnecessary complexity given how rarely this data
  changes; noted as a follow-up if it proves needed.
- **Drop facts/peers/description generation entirely, source them from a different
  (non-LLM) provider** — out of scope; no such structured data source exists for this app
  today, and the LLM-from-search-results approach is the existing convention for enrichment
  fields the app doesn't have a hard data feed for.

## Agent provenance

- **Decided by:** orchestrating Claude agent (main-loop session, no sub-agent dispatch).
- **Lane / branch:** `main`, uncommitted working tree at the time of writing.
- **Alternatives weighed:** see *Alternatives considered* above.
- **Driving artifacts:** this conversation — the owner's screenshot of the Key Facts/Peers
  cards on the MSFT asset-detail page and the direct follow-up question about whether they
  need to be regenerated every refresh.
- **Why this way (one line):** facts/peers/description change on a timescale of weeks or
  months while key_issues must be current every refresh, so gating the slow-changing call off
  entirely once real data exists removes a whole LLM round-trip from the part of the pipeline
  that was actually making refreshes feel slow, without touching the part that must stay fresh.
