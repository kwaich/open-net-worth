# Connector tool-splitting (§B3) and discovery gating (§B2) — build the design

## Context

`.claude/rfcs/2026-08-10-connectors-architecture.md` §B2/§B3 designed, but had not built, two
related pieces of the connector tool surface:

- **§B3**: promote the pre-consolidation per-provider aggregation tool names (`sync_plaid_now`,
  `get_ibkr_status`, …) — currently ALIASES of the consolidated `connector_sync`/`connector_status`
  — back to first-class, separately-schema'd tools, and give the web-search providers
  (Tavily/Perplexity/Serper/Google PSE/DuckDuckGo) the same treatment, which they never had at all
  (`web_search`/`fetch_page` were always generic, provider-blind tools).
- **§B2**: a `connector=` tag on the tool registry, parallel to the existing `mutates=` tag, plus
  teaching `ai/tools/catalog.py` and `find_tools` (`ai/tools/_groups.py`) to hide a
  connector-scoped tool until its connector is enabled — the same "excluded until connected"
  treatment external-MCP tools already get, generalized to native connector-scoped tools.

The RFC's own reasoning (§B3) for reversing the original 16-tool consolidation: once discovery
gating exists, a user only ever sees tools for connectors they've actually enabled (2-4 real
connectors typically, 10 tools worst case for data sources) — half the original 16-tool problem —
and a single shared tool name breaks `ToolGrantStore`'s name-keyed grants (no argument-pattern
grants exist, so "always allow Plaid" on a shared `connector_sync` name would silently also grant
IBKR). This ADR records the concrete decisions made while actually building both pieces, ordered
splitting-first-then-gating per the owner's instruction (gating is more meaningful once the split
tools exist to gate).

## Decision

**Part 1 — tool splitting (§B3).**

Data sources: `PROVIDERS` in `services/aggregation/providers.py` (`plaid`, `enable_banking`,
`yodlee`, `alpaca`, `ibkr` — post the same-day scope-down that removed SimpleFIN/GoCardless/
Pluggy) each got a first-class `get_<provider>_status`/`sync_<provider>_now` pair in
`ai/tools/connectors.py`, promoted from the `_STATUS_ALIASES`/`_SYNC_ALIASES` dicts those exact
names already lived in. Each has its own EMPTY input schema (`_NoArgsInput` — no `providers`
array; the provider is the tool's own identity) and dispatches to the identical
`providers_service.status([key])`/`.sync([key])` call the bulk tools already used; the sync half's
`mutates=` is narrowed statically to that ONE provider's domains (e.g. `sync_alpaca_now` →
`("portfolio",)`, not the bulk tool's `("ledger", "accounts", "portfolio")` superset).
`connector_status`/`connector_sync` are KEPT — the owner's own recommendation, confirmed — now
documented as the explicit BULK convenience ("check/sync several at once"), not the primary path;
`_STATUS_ALIASES`/`_SYNC_ALIASES` are gone from `connectors.py` since their entries are live tools
now, no longer aliases of the merged pair.

Web search: `ai/search/base.py::PROVIDER_REGISTRY` (`duckduckgo`, `tavily`, `perplexity`,
`serper`, `google_pse` — post the same-day scope-down that removed Brave/Exa/Jina/Linkup/SearXNG)
each got `search_via_<id>`/`fetch_page_via_<id>` in a NEW module, `ai/tools/
web_search_providers.py` — genuinely new tools, no aliases to promote (the generic tools never had
a per-provider split). Each resolves its OWN provider directly via `ai.search.base.build_provider`
+ `SearchConfigStore().provider_runtime_config(id)`, bypassing `get_search_provider()`'s
active-selection chain entirely, so `search_via_tavily` always hits Tavily even when a different
provider is marked active — the whole point of picking the named tool over the generic one. An
unconfigured/disabled provider fails with a clear, provider-named message
(`"{label} is not configured — …"` / `"{label} is disabled. …"`) rather than the generic active-
chain error. `web_search`/`fetch_page` are KEPT as the "let the system pick" convenience default,
same reasoning as the data-source bulk pair; their descriptions were updated to point at the named
tools for when a user wants one specifically.

**Registration style differs between the two families, deliberately.** The 10 data-source tools
are hand-authored, one `@tool(...)` block each (matching every other tool in this codebase). The
10 web-search tools are generated by a small `_register(spec)` factory looped once per
`PROVIDER_REGISTRY` entry. This is NOT an inconsistency to fix — `ai/search/base.py`'s own module
docstring states the web-search architecture's whole point: "a new provider is a new module + one
registry entry," with NO other file requiring hand-edits. Hand-authoring 10 web-search functions
would break that promise the moment a 6th provider is added (`PROVIDER_REGISTRY` gets an entry,
but two more functions would still need writing by hand here). The aggregation family has no such
promise — a new aggregation provider always needs a new adapter/orchestrator function written
regardless, so hand-authoring its tool pair costs nothing extra. Each web-search tool still gets
its OWN `@tool()` registration call (own schema-derivation record via `schema_of(model,
tool_name=…)`, own connector tag) — indistinguishable from a hand-written tool to the registry,
`find_tools`, the naming linter, or the golden-schema gate; only the SOURCE authoring is
programmatic.

**Part 2 — discovery gating (§B2).**

`registry.Tool` gained a `connector: Optional[str] = None` field; `registry.tool(...)` gained a
matching `connector=` kwarg, with a docstring paragraph mirroring `mutates=`'s. Two new registry
accessors: `tool_connector(name)` (alias-resolving, mirrors `mutated_domains`) and
`connector_tagged_tools()` (mirrors `mutating_tool_domains`).

Every promoted/new per-provider tool from Part 1 is tagged: `connector="plaid"`,
`connector="web_search:tavily"`, etc. — the EXACT id `services.connectors.list_connectors()`
already assigns that connector's own card (`PLAID_ID = "plaid"`, `_WEB_SEARCH_PREFIX +
provider_id`), so the enablement check is a direct membership test, no separate id-mapping table.
`services/connectors.py` gained `enabled_connector_ids()` — one `list_connectors()` call returning
every currently-`enabled` connector's id, so a caller checking several tags in one pass (building
the whole catalog, or one `find_tools` call) pays for the synthesis once, not once per tag.

A new small module, `ai/tools/_connector_gate.py`, owns the actual gate:
`hidden_connector_tools() -> frozenset[str]` — every connector-tagged tool whose connector isn't
enabled. It fails CLOSED (hides every connector-tagged tool) on any lookup error, matching this
subsystem's existing sibling gates (`catalog._external_sections` hides on a broken external-MCP
manager; `_groups._is_interactive_scope` returns False on any uncertainty) — an enablement lookup
failing must never WIDEN what's offered. `ai/tools/catalog.py`'s `_internal_names()` and
`ai/tools/_groups.py`'s `_candidate_schemas()` both union this hidden set with the pre-existing
`_CATALOG_HIDDEN` set (Task 87's deferred-Tax-tools hide), applied the SAME way — unconditionally,
before any explicit-offer/reachable-universe narrowing — so the two mechanisms behave identically
from a caller's perspective.

**Bulk/multi-connector tools carry no `connector=` tag, by documented convention, not oversight.**
`connector_sync`/`connector_status`/`set_connector_enabled` (data sources) and
`web_search`/`fetch_page` (web search) are left untagged: a single connector id doesn't fit a tool
spanning several/all providers, and gating any of them off would remove the one path that still
works before any single provider is individually configured (`web_search` in particular must keep
working zero-config via DuckDuckGo). Each module's own docstring states this explicitly.

**Discovery-only, never an execution gate — verified, not just asserted.** `assistant.py`'s
ACTUAL dispatch-time auto-load gate (`_is_known_tool`, feeding `_auto_load_and_verdict`) checks
membership against the raw registry (`registered_tool_names()`/`resolve_tool_name`), NOT
`catalog.py`'s or `_groups.py`'s hidden set — confirmed by reading the call site before writing
this gate, not assumed. So a gated tool the model already knows by name (from a prior turn, an
explicit agent `allowed_tools` entry, or a lucky guess) still auto-loads and dispatches; the
underlying handler reports its own `status: "disabled"`, the same self-reporting contract every
aggregation provider already has. This matches the RFC's own B2 framing ("Discovery… is a tool
even offered… Permission… is this call allowed") and keeps "reach never shrinks" — the standing
invariant the 2026-07-18 permission-teardown ADR established for every other discovery mechanism
in this codebase — true for this one too.

## Consequences

### Positive
- The single most concrete win: `ToolGrantStore`'s name-keyed grants can now express "always
  allow Plaid syncs" without silently also granting IBKR, Yodlee, or any other provider that used
  to share the `connector_sync` name.
- A fresh install's tool surface stays small by default — every disabled connector's tools are
  invisible to the catalog/`find_tools` until the user turns it on, without losing the bulk
  convenience path or breaking direct dispatch for a tool the model already knows.
- Zero new domain logic for the 10 data-source tools (same `providers_service` calls); the 10
  web-search tools reuse `WebSearchInput`/`FetchPageInput` and the shared `sanitize_search_results`
  helper (promoted from `misc.py`-private to public specifically for this reuse) rather than
  duplicating the sanitization/schema contract.
- `connector=` is fully generic — the NEXT connector-scoped tool (a future Alpaca-trading tool,
  per RFC §B6's native-completeness roadmap item) gets discovery gating for free by adding one
  kwarg, no new mechanism.

### Negative
- Two tool-registration styles now coexist in `ai/tools/` (hand-authored vs. generated-per-registry-entry)
  — a reader has to learn both. Judged worth it given the two families' genuinely different
  extensibility contracts (see Decision); flagged here so it isn't mistaken for drift.
- The catalog/`find_tools` gate adds one `services.connectors.list_connectors()` call (reading
  ~13 config stores) per catalog build / `find_tools` invocation. Not cached beyond
  once-per-call — matches this file's existing per-turn cost profile (the memory block, skills
  catalog, and FX cache are all recomputed fresh every turn too), but is a real, uncached DB read
  added to a hot path. Flagged as a candidate for measurement if `PERFORMANCE.md`'s wave-benchmark
  harness ever shows it matters; not measured against real session data here.
- Gating applies uniformly even inside an explicit agent offer (`_reachable_universe`'s bound) —
  an agent whose `allowed_tools` names a connector-scoped tool can't `find_tools`-load it until
  that connector is enabled, matching `_CATALOG_HIDDEN`'s existing precedent rather than carving
  out an exception. `_active_tools()`'s own inline agent-offer assembly (`_build_agent_offer`,
  which slices `TOOL_SCHEMAS` directly, bypassing `catalog.py`/`_groups.py` entirely) is
  DELIBERATELY untouched — an agent's pre-declared `allowed_tools` is closer to a permission
  decision than something the model had to discover, and touching it was outside this task's
  scope; noted here as an intentional boundary rather than an oversight so it isn't "fixed" for
  consistency by a future pass without re-litigating this call.

### Follow-ups
- `services/connectors.py::enabled_connector_ids()`'s cost under real load is unmeasured — revisit
  if it shows up in a wave benchmark.
- The permission-wall redesign (RFC §B4, a source-first per-tool grant grid) is a separate,
  still-DESIGNED-not-built piece of the same RFC, actively being iterated by a concurrent lane at
  the time of this change (its wording moved between when this task started and when this ADR was
  written) — genuinely out of scope here, not deferred by this decision.
- RFC §B6 (Alpaca trading as a near-term native roadmap item) is the natural next consumer of
  `connector=` — flagged there already, not restated as new scope here.
- **Deliberately NOT fixed this change**: the post-execution `search_results` citation-chip event
  (`assistant.py`'s `elif tool_name == "web_search":` branch, `_post_execute_events`) and its
  reload-time rehydration counterpart (`_fill_search_block_results`) are still keyed on the
  literal `web_search`/`fetch_page` names only — `search_via_<id>`/`fetch_page_via_<id>` calls
  render as a plain tool pill instead of the richer citation-chip UI. Found by the security
  review below, judged genuinely separate from its actual (security) scope: extending it touches
  a persisted-block/reload-parity contract this change did not otherwise touch, and doing that
  correctly needs frontend verification (`CitationChips.tsx`) this pass could not safely do
  blind. The two SIBLING, lower-risk gaps the same review found — `_TRUNCATE_TOOL_NAMES`
  (history-truncation eligibility) and the PRE-execution `search_start`/`fetch_start` visibility
  events, both purely ephemeral/backend-only with no persisted-block counterpart — WERE fixed in
  this change; see below.

## Security review (2026-08-13, same change)

A `security-reviewer` pass (triggered by this RFC's own security-critical-areas list: external
I/O, and CLAUDE.md's "touches money, auth, or external I/O" DoD gate) traced — not just read the
docstrings of — the SSRF guard, the sanitization pipeline, the secret-hiding contract, the
fail-closed gate, and the layer contracts. Six of seven numbered checks PASSED outright (SSRF
guard ordering verified byte-for-byte against `fetch_page`'s own; sanitization reuses the shared
helper, no parallel copy; discovery-gate fail-closed path traced through `_connector_gate.py` and
exercised by a monkeypatched test, not assumed; the narrowed per-provider `mutates=` tag was
checked against `_confirm_gate.is_gated_tool` specifically to confirm the confirm-gate still
fires; import-linter re-run clean). One genuine finding, fixed in this same change:

- **MEDIUM — Google PSE API key leak via an unredacted HTTP error.**
  `GooglePseProvider.search` (`ai/search/google_pse_provider.py`) puts `key=<api_key>` directly
  in the request URL's query string; `httpx.HTTPStatusError`'s own message embeds the full
  request URL, verified concretely against a real 403 response shape. The bare `raise` in
  `web_search_providers.py::_search_via` (and the pre-existing equivalent in `misc.py::web_search`
  when Google PSE happens to be active) propagates that string into the tool result JSON, the
  persisted session transcript, and `LOGS_DIR`. Real trigger: any Google PSE 4xx/5xx — an expired
  key, a quota cap, a disabled project. **This diff makes a previously-LATENT leak newly
  REACHABLE**: pre-split, it only fired when Google PSE was the store's *active* provider (last in
  catalog order, so rarely active with any other keyed provider enabled); `search_via_google_pse`
  reaches it directly regardless of which provider is active — exactly the configuration this
  RFC's whole point is to enable (Tavily active day-to-day, Google PSE also configured and
  individually callable). **Fixed at the source**, not just in the new module: `search()` now
  catches `httpx.HTTPStatusError`, strips the query string (key, cx, AND the user's search text —
  defense in depth, none of the three need to ride an error message) via
  `exc.request.url.copy_with(query=...)`, and re-raises a redacted `HTTPStatusError` carrying only
  the status code. Fixing it here (not in `web_search_providers.py`'s own except-clause) closes
  the gap for every caller — `web_search`, `x_search`, and `search_via_google_pse` alike — instead
  of patching only the newly-reachable path. Covered by 4 new tests in
  `tests/test_search_provider.py` that exercise a REAL `httpx.HTTPStatusError` (a stubbed
  `raise_for_status()`, not a hand-built exception string), so a future change that stops calling
  `raise_for_status()` the same way trips them: key redacted, cx+query redacted too, status code
  still surfaces, and the success path is provably untouched.
- **LOW — `_TRUNCATE_TOOL_NAMES` (`assistant.py`) missed the 10 new web-search tools.** They
  produce the identical verbose free-text `web_search`/`fetch_page` do, but weren't in the
  history-truncation eligibility set — fixed by deriving the set from `ai.search.base
  .PROVIDER_IDS` instead of hand-listing two names, so a future provider needs no matching edit
  here either.
- **LOW — the pre-execution `search_start`/`fetch_start` SSE visibility events were also keyed on
  the literal two names.** Fixed (extended the same two `if`/`elif` branches) since these events
  are purely ephemeral (fire once, pre-execution, no persisted/rehydrated counterpart to keep in
  sync) — safe to extend without touching the citation-chip/reload subsystem flagged as
  out-of-scope above.
- **NIT — no direct secret-hiding test for the promoted `get_plaid_status` tool** (existing sweeps
  all went through the bulk `connector_status`). Added
  `test_promoted_get_plaid_status_tool_hides_secret_too` in `tests/test_tools_aggregation.py`.

## Alternatives considered

- **Tag the bulk tools with a synthetic multi-connector value** (e.g. a list, or a shared
  namespace prefix) so they participate in gating too. Rejected: a single connector id is the
  contract every consumer of `connector=` expects (one tag → one enablement check); a
  multi-connector shape would need its own separate code path in both `catalog.py` and
  `_groups.py` for one tool family, for a benefit (hiding `connector_sync` before ANY provider is
  configured) that actively contradicts what makes the bulk tools useful as a fallback.
- **Retire `connector_sync`/`connector_status`/`web_search`/`fetch_page` outright** once the
  per-provider tools exist, mirroring the `fetch_emails` retirement precedent
  (`2026-08-12-email-search-hydrate-split.md`). Rejected per the owner's own recommendation in the
  task: keep both, explicitly positioned as bulk-vs-single, rather than force every "check
  everything" or "just search" call through N separate tool calls.
- **Hand-author all 10 web-search tools**, matching the data-source family exactly, for
  consistency of style. Rejected — see Decision's "registration style differs" note: it would
  quietly break `PROVIDER_REGISTRY`'s own "one registry entry, no other file to touch" contract
  for future providers.
- **Cache `enabled_connector_ids()` across calls within a turn** (e.g. a ContextVar) to avoid the
  repeated `list_connectors()` read. Rejected for this change: no measured evidence it's a real
  cost yet (see Negative/Follow-ups), and every sibling per-turn computation in this codebase
  (memory block, skills catalog, FX cache) already accepts the same per-call cost — adding a new
  caching seam without a measured justification would be premature.
- **Gate execution too** (refuse a disabled connector's tool call outright at dispatch, not just
  hide it from discovery). Rejected — this is exactly the discovery/permission conflation RFC §B2
  exists to split apart; every aggregation provider already self-reports `status: "disabled"`
  rather than raising, and a hard block would be a second, redundant mechanism doing the same job
  worse (a raised error a caller has to catch, instead of a structured status a caller already
  reads).
