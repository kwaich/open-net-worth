Help the user author a new Lucius skill and iteratively improve it (adapted from Anthropic's skill-creator). At a high level the process is: figure out what the skill should do → draft it → test it on 2-3 realistic prompts → review the results with the user → rewrite from their feedback → repeat until they're happy. Figure out where the user is in that arc and jump in there. If they just want to vibe and skip the testing loop, do that — the loop serves the user, not the other way around.

A skill is clear markdown instructions plus a precise description that says both what it does and when to use it. It does not grant, hide, allow, or deny tools: Lucius uses ordinary tool discovery and every app-wide confirmation/security rule still applies. When the skill needs a deterministic computation the model can't do reliably in its head (combinatorics, precise decimal math, fiddly parsing), bundle a short script — Python, Bash, or Node — that reads JSON from the SKILL_INPUT env-var path and prints JSON to stdout. Saving a bundled script does not enable code execution: the operator must turn on Bundled script skills in Settings → Developer, with a separate switch for unattended runs.

METHOD:
1. CAPTURE INTENT. If this conversation already contains the workflow ('turn this into a skill'), extract it from the history first — the tools used, the step order, corrections the user made — and have the user confirm the gaps. Otherwise establish: what should the skill enable Lucius to do; when should it trigger (what would the user actually say); what should the output look like; and whether to test it after (objectively checkable outputs benefit from test prompts; subjective ones often don't — suggest a default, let the user decide). If the topic is vague, ask one or two focused questions — do not guess. Research before asking: peek at the user's real data with the read tools the skill will use, so you come prepared.
2. NAME + TRIGGER. The automatic catalog contains the description — put trigger information there, not in the body: "Use this skill to …", the user intents and phrasings that should invoke it, and a "Not for …" sentence naming the near-misses (a sibling skill, a one-off question). Under 1024 characters. Skills under-trigger far more than they over-trigger, so make the description a little pushy — name the adjacent phrasings, not just the obvious one. Short slug name. Worked makeover: read_skill_file('references/examples.md').
3. DESIGN THE BODY. Keep SKILL.md to what is needed on EVERY run — about 100 lines: a Gotchas section (the non-obvious corrections), a numbered checklist, and the output contract. Detail needed at one step (a field catalogue, worked examples) goes in references/<name>.md with the step that reads it named in the body; a fixed output design goes in assets/ as a template. Pass them as create_skill's `files`. Name any ordinary tools the workflow should use and confirm EVERY one is real. The skill itself never changes tool availability; ordinary discovery loads tools when needed and app-wide policy still decides execution. If a needed tool doesn't exist, say so and stop; never invent a tool name. If a deterministic computation is needed, draft the short script (stdlib only; SKILL_INPUT JSON in, JSON out). Either way: write imperatively, and explain WHY an instruction matters instead of stacking all-caps MUSTs — a reason beats a shouted rule. If output shape matters, give an exact template. Keep it general — the skill should work on many future prompts, not just today's example.
4. INPUT. Read task-specific input from the user's current conversation. Skills do not define a separate argument or template language.
5. SAFETY. A skill never applies a money change or external action the user hasn't agreed to: it proposes the change and asks first. Whether the app then shows its own approval card is the user's permission setting, not the skill's — never write that a step "shows a confirm card", and never rely on one. And a skill's contents must never surprise the user given its name and description.
6. CREATE IT. Draft a clear, numbered markdown body: which tools to call in what order, how to read the results, what to report. Currency-neutral — surface amounts in whatever base currency the tools report; never hardcode a currency. Then call create_skill (instructions-only) or save_code_as_skill (with a bundled script — pass name, source, instructions, description). Present the draft and ask the user before you save it; their permission settings decide whether the app also shows an approval card. If a script is bundled, tell the user plainly it's saved DISABLED and how to enable it.
7. TEST & ITERATE. Draft 2-3 realistic test prompts — the kind of thing this user would actually type, concrete and specific. Show them first: 'Here are the test prompts I'd like to try — do these look right, or want to add more?' Run each with activate_skill, one at a time, and show the user the prompt and the output BEFORE judging it yourself — their eyes first. Ask what they'd change, improve with update_skill, and rerun. Stop when the user says they're happy, the feedback comes back empty, or iteration stops making progress. Full loop + improvement principles: read_skill_file('references/testing-and-iteration.md').

REFERENCE DOCS — load ON DEMAND with read_skill_file, never all up front: references/authoring-guide.md (the full method: capture intent, descriptions-as-triggers, ordinary tool references, writing style, splitting a skill into body + references/ + assets/, safety), references/testing-and-iteration.md (the test loop, how to think about improvements, trigger-testing the description), and references/examples.md (two worked examples and a description makeover). Read the one you need when you reach that step.
