# Acceptance — Mobile shell: bottom tab bar + Lucius as a plain in-flow tab

Design authority: `.claude/rfcs/mobile-shell-tabbar-and-lucius-sheet.md` (tab bar shape) +
`docs/adr/2026-07-22-lucius-tab-not-sheet.md` (Lucius's own rendering, superseding that RFC's
bottom-sheet mechanics) + `docs/adr/2026-08-06-mobile-tab-bar-drops-to-three-money-destinations.md`
(amends the slot count/position: five slots, not six) + the Open Design artifact `Mobile Shell.html`
(project "Open Net Worth UI"). Verify on the running app via `make qa-e2e` / `make qa-cu` at a
**390×844** viewport, never `:5174`/`:8080` directly.

## MB1 — Bottom tab bar replaces the hamburger drawer
- **MB1.1** GIVEN the viewport is < 640px WHEN any tab loads THEN a fixed bottom tab bar (`.mb-tabbar`) is present with exactly 5 slots, in order — Overview, Accounts, **Lucius**, Investments, More — and the `.topbar-hamburger` is NOT rendered. Lucius sits at the true center of the bar (two slots either side — `docs/adr/2026-08-06-mobile-tab-bar-drops-to-three-money-destinations.md`), not trailing at the far right. Plan (the `transactions` tab) is not a tab-bar slot — it lives in the More sheet's Sections group (MB2.1), the least-often-tapped of the four money destinations by the shipping engineer's judgment.
- **MB1.2** GIVEN the tab bar WHEN a slot is tapped THEN the route changes to that tab, the slot takes `.active` (ink icon + label, `var(--primary)` top indicator), and the previously active slot returns to `var(--faint)`.
- **MB1.3** GIVEN a deep route (e.g. `/asset/$instrumentId`, `/accounts/payees`) THEN the tab bar still renders and the owning parent tab reads as active — the bar never disappears mid-flow.
- **MB1.4** GIVEN each slot THEN its hit area is ≥44×44 CSS px and the bar's bottom padding includes `env(safe-area-inset-bottom)` (no slot sits under the home indicator).
- **MB1.5** GIVEN the viewport is ≥ 640px THEN the tab bar is absent and the desktop sidebar/rail is byte-identical to `main` (screenshot diff).
- **MB1.7** GIVEN any reachable state of the shell THEN **exactly one** slot reads as active and exactly one carries `aria-current="page"` — the bar takes a single selection value (`MobileNavTarget = TabId | 'lucius'`), never an `(activeTab, luciusOpen)` pair that consumers reconcile per slot. A tab demoted into the More sheet is represented by the More slot. Regression: `MobileTabBar.test.tsx` MB1.4.
- **MB1.8** GIVEN Lucius is the open tab WHEN the route changes by ANY means — a tab-bar slot, a More-sheet row, the command palette, an in-tab "go to …" link, or the browser's back — THEN Lucius closes and the destination renders. Since 2026-09-05 this is structural, not a rule: on a phone Lucius IS the `/lucius` route (`docs/adr/2026-09-05-phone-lucius-is-the-lucius-route.md`), so leaving it is leaving a route. There is no separate "chat open" flag on a phone for a call site to forget (the desktop dock keeps its own, `useLuciusTab`, which the phone never reads). Regression: `useLuciusTab.test.tsx` pins the flag as desktop-only.
- **MB1.9** GIVEN any surface anchored to the bottom of the viewport (toast, bulk bar, undo strip, rail FAB) THEN it clears `.mb-tabbar` by carrying the `mb-anchored` utility class — the shell does not enumerate component class names. Regression: `mobileClearance.contract.test.ts`.
- **MB1.10** GIVEN the viewport is < 640px THEN `.topbar` carries no content at all (see MB2.6) and collapses to **exactly the status-bar inset** — `padding-top: var(--safe-t)`, no other padding or margin — so it is **zero-height in a browser** and a tab's own header sits at the very top of the screen, and an opaque strip under the notch in a standalone PWA. Its background stays the flat `var(--bg)` of the base rule: a `linear-gradient` built from `color-mix()` + `var()` computes to `initial` — i.e. TRANSPARENT — on any engine that can't substitute it (it does NOT fall back to the earlier declaration), which makes the mask silently vanish on device while looking correct in headless Chromium.
- **MB1.11** GIVEN any tab that renders the generic `.tab-header` THEN on a phone that header is **sticky** at `top: var(--safe-t)`, opaque, and bled past the pane's side padding (`box-shadow: 0 0 0 100vmax`/`clip-path`), so scrolling content passes UNDER it and never appears above it. GIVEN Overview (its own header) THEN on a phone the title row is **static** and only `.ov-view-tabs` pins, at the CONSTANT offset `top: var(--safe-t)` — not at the JS-measured `--ov-topbar-h` + `--ov-header-h` stack the desktop uses, whose stale measurements pinned the header half-collapsed ("moves a bit then stops", title clipped mid-glyph). Measured at 390×844, scroll ∈ {0, 60, 150, 400, 900}: the pinned row settles at `y = 0` (safe-t 0) / `y = 59` (safe-t 59) and does not move again; `elementFromPoint` finds nothing but the strip above it. `--ov-topbar-h`/`--ov-header-h` are still measured for desktop, and the measuring effect now re-runs when the header mounts (deps, not `[]`) instead of leaving the 56px CSS fallback in place forever on a cold load.
- **MB1.12** GIVEN the app is open in an iOS browser tab with Safari's bottom toolbar expanded THEN the shell uses the small viewport (`100svh`), releases the desktop shell's `min-height: 100vh` floor, and every tab-bar control is fully above the browser chrome; GIVEN the app is installed/standalone THEN it keeps `100dvh` and has no browser-sized dead band. Regression: `mobile-bottom-clearance.test.ts`; real-device sign-off covers both display modes.
- **MB1.6** GIVEN any tab with scrollable content WHEN the page is scrolled (including into an iOS/Android overscroll bounce at the top or bottom) THEN `.mb-tabbar` never moves, never lags, and never shows a gap of background behind it — it is `position: fixed` to the viewport, the document root carries `overscroll-behavior-y: none`, and the bar casts an upward `box-shadow` so it reads as elevated above the content, like a native tab bar, rather than flush with it.

## MB2 — The More sheet carries the rest of the IA
- **MB2.1** GIVEN the More slot WHEN tapped THEN a bottom sheet (`.mb-sheet`) rises over a tap-to-dismiss scrim, with a drag handle and two labelled groups: "Sections" (Plan, Commitments, Intel — 'Tax' and 'Inbox' deliberately excluded, hidden pending further work, Task 87) and "Manage" (Automations, Skills, Connectors, Settings). Plan joined Sections in the 2026-08-06 tab-bar rework (`docs/adr/2026-08-06-mobile-tab-bar-drops-to-three-money-destinations.md`); 'Build' is likewise excluded from Manage, same treatment as Tax/Inbox; 'Profile' has no row of its own — it is the first SECTION of the Settings overlay (2026-08-05 redesign), not a separate destination.
- **MB2.2** GIVEN the sheet WHEN a row is tapped THEN the sheet dismisses and the app navigates to that tab.
- **MB2.3** GIVEN the sheet WHEN the scrim is tapped, the handle is dragged down, or Escape/back is pressed THEN it dismisses without navigating.
- **MB2.4** GIVEN the Inbox unread count is > 0 THEN a `var(--bad)` dot badge shows on the More slot AND the Inbox row inside the sheet shows the count — a pending item is never hidden by the demotion.
- **MB2.5** GIVEN the sheet is open THEN the page behind does not scroll, and focus is trapped in the sheet.
- **MB2.6** GIVEN the viewport is < 640px THEN the topbar's "As of … · Prices: live/loading/cached" stamp is NOT rendered on any tab; it renders instead in the More sheet's **header**, directly under the "More" title, as a status line (`.mb-sheet-stamp`, `--muted`; `Prices: live` in `--good`). Header, not the scrolling body: a footer row sat below the fold and under the home indicator, so reading status meant scrolling a navigation sheet. It is not a tap target. Regression: `MobileTabBar.test.tsx` MB2.6. Rationale: on a phone the stamp was the topbar's ONLY content (hamburger → tab bar, Search/privacy/Lucius → sheet and slots), so it cost a full row of a 390px screen on every tab.
- **MB2.7** GIVEN Settings was opened from the More sheet's row WHEN it is dismissed THEN the app is back on the page that was underneath, alone — the More sheet does NOT rise again. Settings is a sheet over your work (the sheet model), not a level inside More (the stack model). The stack model was built, used on the phone and reverted the same day by the owner ("not a good UX"): `docs/adr/2026-09-05-settings-from-more-returns-to-more.md`, status Reverted.

## MB3 — Lucius is a tab bar item, rendered as an ordinary tab (not a sheet)
Superseded again 2026-07-22 (task 90) — see `docs/adr/2026-07-22-lucius-tab-not-sheet.md`, which
supersedes `docs/adr/2026-07-22-lucius-tab-bar-item.md`'s "full-snap bottom sheet" shape (itself
built on `docs/adr/2026-07-22-mobile-lucius-fab-not-bar.md`). The owner reported the full-snap
sheet still *read* as a floating popup — rounded top corners, a violet top border, a drop shadow,
a drag handle, trailing at the far right of the bar — rather than as a normal tab. Lucius now (1)
sits in the **middle** of the tab bar — **3rd of 5**, between Accounts and Investments (moved off
4th-of-6 by `docs/adr/2026-08-06-mobile-tab-bar-drops-to-three-money-destinations.md`, which cut
Plan from the bar so an odd slot count gives Lucius a true center — MB1.1) — and (2) renders
**inline inside `.app-layout`**, in place of whatever tab was previously showing, with zero
floating-sheet chrome: no `.mb-lucius-sheet`, no scrim, no drag handle/snap points, no rounded top
corners, no colored border, no box-shadow. It occupies the content area exactly the way any other
tab (e.g. Accounts, itself a fixed-height "panel" tab) does.
- **MB3.1** GIVEN the viewport is < 640px THEN the floating `.lx-dock` pill is NOT rendered and no floating Lucius button is rendered; the tab bar's Lucius slot (3rd of 5) is the one entry point.
- **MB3.2** GIVEN a turn is streaming THEN the Lucius slot's icon is replaced by the existing spinner treatment (`.lx-dock-dot`, recolored off `currentColor` for the plain tab-bar surface).
- **MB3.3** GIVEN a turn has completed while Lucius is closed THEN the Lucius slot shows a small dot badge (`.mb-tab-badge`, the same badge every other slot uses for a pending item); the badge is not shown while the tab is active — an answer you're already looking at is not "unread".
- **MB3.4** GIVEN the Lucius tab WHEN tapped THEN the app navigates to `/lucius` — a route, exactly like every other slot — and `.app-layout` renders the phone's Lucius surface (`LuciusMobile`, `.app-layout--lucius`) filling the content area between the topbar and the tab bar, composer focused, with the slot `.active`; GIVEN any OTHER tab-bar destination (a primary slot, or a More-sheet row) WHEN tapped while Lucius is open THEN the route changes and that destination's own content renders — the two are never simultaneously "the active tab". The conversation itself is preserved and resumes exactly where it left off next time the Lucius tab is opened.
- **MB3.5** GIVEN Lucius is the open tab WHEN an overlay is opened over it and dismissed — Settings from the More sheet, Help — THEN the app is back on `/lucius` with Lucius showing — and Lucius stayed MOUNTED under the sheet the whole time (what renders is the tab under the overlay, `tabToRender`, while the bar lights More), so the sliver the 92dvh sheet leaves visible is Lucius and the dismiss reveals it rather than cold-mounting it — because the overlay's "where I came from" is the route and Lucius is one (owner, 2026-09-05: "I was at Lucius, after going back from settings it goes back to the one before Lucius tab which is dashboard"). Likewise the browser's back from a later tab returns to `/lucius`, and a stale desktop `chat-open` flag in localStorage never shows Lucius on a phone: only the route does. Every in-tab "Ask Lucius" / "open the chat" affordance (Overview's suggestions, Plan/Commitments/Intel's Ask Lucius, Skills' run, Automations' open, the palette's Ask Lucius, the long-press `lx-dock-open` signal) goes to `/lucius` on a phone and opens the side dock on desktop — one `openLucius` in `RouterShell`.
- **MB3.5** GIVEN the Lucius tab is open THEN the content area carries no border-radius, no colored border, and no box-shadow — visually indistinguishable in chrome from any other tab's content area — and its header is the existing `.lx-side-head` content (spark + "Lucius" + conversation switcher + close) with the generic `tab-header` (title/subtitle) suppressed, same as every other self-headered tab (Accounts, Plan, …).
- **MB3.6** GIVEN the Lucius tab is open THEN the composer's screen-context row (`ScreenContextBar` — the "can see this screen" toggle + Peek) is NOT rendered, and no screen snapshot is attached to a sent turn regardless of the user's global screen-awareness preference — `ChatPanel`'s `screenAwarenessDisabled` prop is `true` for this instance only; the desktop side panel and dock are unaffected.
- **MB3.7** GIVEN the soft keyboard opens WHEN the composer is focused THEN the composer stays visible directly above the keyboard, the bottom navigation remains anchored at its normal layout-viewport position behind the keyboard (never between the composer and keyboard), and the message list scrolls to the latest turn.
- **MB3.8** GIVEN the Lucius tab is tapped open THEN the composer is NOT autofocused and no keyboard is raised — the tab is readable and `.mb-tabbar` stays visible. Desktop and the long-press "Ask Lucius about this" path still focus.
- **MB3.9** GIVEN any phone viewport THEN `.mb-tabbar` is **not** `position: fixed` — the shell is a `100dvh` flex column, the content pane is the only scroller, and the bar is its last in-flow row. iOS re-anchors fixed elements to the keyboard; an in-flow row cannot be moved by it. Regression: `mobile-bottom-clearance.test.ts` + `node frontend/qa/investigate-keyboard.mjs` (reports `bar position: static`).
- **MB3.10** GIVEN `index.html` THEN its viewport meta carries `interactive-widget=resizes-content`, so the keyboard shrinks the layout viewport and `100dvh` stays truthful with no JavaScript.
- **MB3.11** GIVEN any text-entry field takes focus THEN `.mb-tabbar` is `display: none` and `--mb-tabbar-h` is `0px` — immediately, in CSS, with no measurement. `<select>` and the input types that raise no keyboard (`file`, `checkbox`, `radio`, `range`, `color`, `submit`, `button`) are excluded. Regression: `mobileKeyboard.contract.test.ts`.
- **MB3.12** GIVEN the codebase THEN there is **no keyboard-measuring hook** and no `mobile-keyboard-*` class. Six attempts at inferring the keyboard from `visualViewport` failed; the constants they required described nothing real. Pinned by `mobileKeyboard.contract.test.ts` ("has no keyboard-measuring hook at all").
- **MB3.12** CSS half, measured against the real stylesheet in a real browser at 390×844: `node frontend/qa/measure-keyboard-tabbar.mjs` — with `.mobile-keyboard-open` on `<html>`, `.mb-tabbar` computes to `display: none`, `--mb-tabbar-h` to `0px`, and an `.mb-anchored` surface drops to the bottom edge. No backend, no API key.

## MB4 — Retired (task 90)
Retired — Lucius no longer renders as a bottom sheet with snap points (peek/half/full), a drag

## MB5 — Touch replacement for drag-into-Lucius
- **MB5.1** GIVEN any row with `data-entity-id` WHEN long-pressed (~500ms) THEN a context menu appears offering "✦ Ask Lucius about this" / "Open" / "Copy", and the row shows the existing violet `.drop-target` outline while pressed.
- **MB5.2** GIVEN "Ask Lucius about this" is chosen THEN the Lucius tab opens with that entity attached as a chip in the composer — identical chip identity to the desktop drag path.
- **MB5.3** GIVEN a long-press that turns into a scroll THEN the menu does NOT open (the gesture cancels cleanly).
- **MB5.4** GIVEN a long-press on a row THEN ONLY our menu appears — no iOS text selection or Copy / Look Up / Translate callout on top of it (rows are `user-select: none` / `-webkit-touch-callout: none` on a phone; any selection that raced in is cleared) — and lifting the finger does NOT open the row's detail screen (the synthesized click is swallowed once). On Android the native `contextmenu` for the same press opens the menu exactly once, at one position (owner report, 2026-09-08).
- **MB5.5** GIVEN a long-press near any viewport edge THEN the menu is fully visible, pulled inside the viewport with an 8px margin — never cut off.
- **MB5.6** GIVEN the menu is open WHEN the user taps anywhere outside it (including the row itself, to open its detail), scrolls, presses Escape, or the screen changes underneath it (the row leaves the DOM) THEN the menu closes immediately; a tap on the menu's own button still fires.
