# Derive tool `input_schema` from typed models

- **Date:** 2026-07-19
- **Status:** Accepted (mechanism shipped; migration incremental)
- **Scope:** `backend/ai/tools/` — the 272 `@tool` schemas
- **Agent provenance:** built on the `harness/reliability-program` branch, additive-only
  lane (five other lanes held most of `backend/ai/tools/` concurrently).

## Context

Every tool declares an `input_schema` dict **by hand, separately from the handler that
reads it**. Nothing keeps the two in agreement, and measurement says they routinely
disagree:

- ~50 stale descriptions (17%) — prose describing a parameter the handler renamed.
- Handlers reading parameters the schema never declares. `test_rule` reads
  `override_existing` and `stop` under `additionalProperties: false` — **unreachable**.
- `required` naming fields the handler treats as optional (`add_transactions` requires
  `category`, which the documented invariant calls optional).

This is also why `registry.validation_error` can only enforce *effective types*. The long
note there records the finding directly: **the declared schemas do not describe what the
handlers accept**, so they cannot be enforced. An attempt to enforce `required` /
`additionalProperties` / `enum` broke calls that work today.

Claude Code's own tools take the inverse approach — its shipped `sdk-tools.d.ts` says
*"automatically generated by json-schema-to-typescript. DO NOT MODIFY BY HAND."* One
artifact, mechanically projected, compiler-checked. Its schemas can be strict because they
are not a claim *about* the code — they **are** the code. Python's natural direction is the
mirror image: types → schema, via Pydantic.

## Decision

Introduce `backend/ai/tools/schema_from_model.py`: `schema_of(Model)` projects an
Anthropic-shaped `input_schema` from a Pydantic model. A tool declares its parameters once,
as a model; the schema is derived. **A parameter the handler does not read cannot appear in
the schema, because the schema IS the model.**

Migration is incremental and additive. A derived tool registers alongside a literal one
with **zero changes to `registry.py`** (verified: mixed registry, `build_tool_schemas()`
and dispatch both unaffected).

### The five transforms

`model_json_schema()` is close to Anthropic's shape but not equal to it.

| # | Pydantic emits | We emit | Why |
|---|---|---|---|
| 1 | `$ref` + `$defs` | inlined | every hand-written schema here is self-contained |
| 2 | `anyOf: [X, {"type":"null"}]` | `X` | Pydantic's spelling of `Optional[X]` |
| 3 | `title` per field | dropped | no hand-written schema carries the keyword; pure prompt weight |
| 4 | `default: null` | dropped | optionality residue; a **real** default survives (5 tools declare one) |
| 5 | class docstring → root `description` | dropped | engineer-facing doc, not model-facing prose |

**Transform 5 was not predicted.** The enforcement assertion caught it on its first run —
the mechanism working as intended. It is suppressed in `ToolInput.__get_pydantic_json_schema__`
rather than by matching `cls.__doc__` in the walk, because that also covers nested models
inlined from `$defs`, where the docstring is unreachable from the JSON.

### Every walk is structure-aware

A keyword is only a keyword in keyword position. Three tools (`create_artifact`,
`schedule_task`, `update_scheduled_task`) have a parameter **literally named `title`**, and
`forget_fact` has one named `description`. A naive `pop("title")` would silently delete a
*required* parameter from `create_artifact`. `schema_from_model` therefore imports its
keyword classification from `registry._SCHEMA_*_KEYWORDS` rather than re-declaring it — a
divergence between the two walkers is exactly the bug class this module exists to prevent.

## The enforcement assertion

`tests/golden/tool_input_schemas.json` pins the `input_schema` all 272 tools emitted
**before** any derivation work started. `tests/test_schema_from_model.py` provides
`assert_derived_matches_literal(tool_name, Model)` and asserts:

- every **migrated** tool still emits byte-for-byte what it emitted as a literal
  (auto-collected from `derived_schemas()` — no hand-maintained list);
- every **unmigrated** tool still matches its pin, so drift anywhere is caught.

This makes migration mechanical: write the model → swap the schema → run the test → a
mismatch is a red diff, never a silent behaviour change.

The golden file is **deliberately not auto-regenerated**. Changing a schema on purpose
means editing it by hand — which is exactly the review moment this design wants to create.

> **A green assertion is not a correctness proof.** It proves the model sees *no change*.
> It does **not** prove the schema is *right*. Where the pinned literal is wrong, byte
> identity faithfully preserves the wrongness. Fixing a schema is a separate, deliberate
> commit that edits the golden file and says why.

## Re-measured quirk inventory (this lane, by execution)

A prior sketch reported "only 25 sites, 96% clean." **Both numbers are wrong** — it
counted only nested objects reachable through `properties`, missing those under `items`.

| Class | Tools affected | Policy |
|---|---|---|
| Nested object without `additionalProperties` | **37** | nested model **without** `extra="forbid"`; needs a non-`ToolInput` base — see below |
| Root without `required` | 7 | omit only if the literal omits it; `schema_of` injects `[]` by default |
| Root without `additionalProperties` | 4 | do **not** use `ToolInput` as-is (propose→apply replay dispatches stored change dicts carrying `type`/`display`/`reason`/`idempotency_key`) |
| `type: ["x","null"]` nullable | 3 | `explicit_null()`, opt-in — **migrate last, human decision** |
| `oneOf` (`set_plan_baseline.baseline`) | 1 | hand-write or `Union` + manual check |
| Multi-branch `anyOf` (`get_transactions`) | 1 | `Union[...]`; transform 2 only collapses the exact 2-branch X-or-null shape |

**Distinct quirky tools: 50 of 272 → 222 structurally clean (81.6%)**, not 96%.

### The three nullables — why they are last

`update_transaction.payee_id`, `bulk_update_transactions.payee_id`, and
`set_payee_default_category.category` spell nullability as `{"type": ["string","null"]}`,
and the difference is load-bearing: **passing `null` clears the stored value; omitting the
key leaves it untouched.** A plain `Optional[str]` would be collapsed by transform 2 to a
bare `{"type":"string"}`, silently removing the model's ability to clear a field on money
records. They must opt in via `explicit_null("string")`, and a human should confirm each.

## Findings — derived vs. literal

Five tools migrated as proof: `get_tax_loss_harvest`, `get_tax_report`, `get_tax_estimate`,
`remember_fact`, `forget_fact`. All five derive **byte-identically**. Findings:

1. **Generator gap (fixed):** the class docstring leaking into the schema as a root
   `description`. Caught by the assertion, closed as transform 5.
2. **Not a bug, contrary to first read:** `get_tax_report` / `get_tax_estimate` declare
   `year` required while both handlers read it as `input_data.get("year")`. This *looks*
   like the declared-required-but-unenforced class catalogued by the write-choke audit, but
   enforcement is real one layer down — `tax.validate_year` does `int(None)` →
   `ValidationError("year must be an integer")`. The declaration is honest. Recorded
   because the tempting "fix" (relaxing `year` to optional) would have been wrong.
3. **Genuinely enforced:** `remember_fact.content` and `forget_fact.description` are read
   as `input_data["content"]` / `["description"]` — a `KeyError` on absence. `required` is
   backed by code.

### Interaction with the write-choke audit

A parallel lane found only ~33 of 236 fields across the ten `apply_*_change` chokes are
enforced by code, including two live money bugs: `quantity` is declared **required** on
`apply_lot_acquire` / `apply_position_add` but neither enforces it
(`float(change.get("quantity") or 0)` → a quantity-less acquire **silently books zero
units**), and `apply_vest`'s handler raises `"fmv_currency is required"` for a field the
schema does **not** mark required — so a caller obeying the schema constructs a call
guaranteed to be rejected.

Two consequences for this mechanism:

- **A `required` mismatch during migration should be treated as a probable schema bug, not
  a generator gap.** Report it with the handler line that proves it; do not adjust the
  model until it matches.
- **Do not try to derive required-ness from the handler** — mostly it is not there to
  derive. A model's `required` is a *declaration the author makes*. That is appropriate,
  but it is a new claim, not a recovered one. Where the handler enforces nothing, say so
  rather than silently blessing the existing list.

Once schema and handler come from one artifact, this entire class —
declared-required-but-unenforced, enforced-but-undeclared — becomes **structurally
impossible** rather than something an AST audit has to go hunting for.

## Recommended migration order

1. **The 222 structurally-clean tools**, file by file, in files no other lane holds.
   Mechanical: model → `schema_of` → assert → next.
2. **The 7 roots without `required`** — trivial, but keep the omission (do not let
   `schema_of` inject `[]` where the literal has none).
3. **The 37 nested-object tools.** Needs one addition first: a nested-model base that does
   *not* set `extra="forbid"`, so a nested object derives without
   `additionalProperties: false`. Do this once, not per tool.
4. **The 4 roots without `additionalProperties`** — read the replay paths
   (`mcp/proposals.py`, `connectors/chat/confirm.py`, `api/agents.py`) before touching.
5. **`set_plan_baseline` (`oneOf`) and `get_transactions` (multi-branch `anyOf`)** — one
   each, hand-considered.
6. **The 3 nullables, last, with a human confirming each.**

## Honest effort estimate

Grounded in the five migrated here (~10 min each including the description move, once the
adapter existed):

| Bucket | Tools | Estimate |
|---|---|---|
| Clean (705 properties, avg 3.2/tool) | 222 | ~2–3 focused days, parallelisable by file |
| Roots without `required` | 7 | <1 hour |
| Nested objects (249 properties) | 37 | ~1 day **after** the nested-base addition (~1 hour) |
| Roots without `additionalProperties` | 4 | ~2 hours (needs replay-path reading) |
| `oneOf` / multi-`anyOf` | 2 | ~1 hour |
| The 3 nullables | 3 | ~1 hour + human review |

**Total ≈ 4–5 engineer-days**, safely incremental — every step is guarded by the golden
file, and a half-finished migration is a valid state (mixed registry is proven).

The prize is not the schemas. It is that afterwards `registry.validation_error` can be
tightened from *effective types* toward real enforcement, because the schemas will finally
describe what the handlers accept.

## Consequences

- **Additive.** Nothing forces migration; 267 literals are untouched and pinned.
- **New dependency edge:** `backend/ai/tools/` now imports `pydantic` (already a project
  dependency; `ai/routing/types.py` precedent). All 5 import-linter contracts stay green.
- **The golden file is a maintenance obligation** — a genuinely new tool must be added to
  it deliberately. That is the intended friction.
- Descriptions move **verbatim**. No prose was regenerated in this lane.

Two additions to the mechanism, both used and pinned:

- **`schema_of_no_required(model, tool_name=...)`** (Phase 2 of the recommended order) —
  omits the root `required` key entirely rather than defaulting to `[]`, for the 7 tools
  whose literal spells "nothing required" that way. Refuses a model that actually declares
  a required field (a real signal, not a spelling choice). Used for
  `list_scheduled_tasks`, `list_import_batches`, `delete_transactions_where`.
- **A genuinely new quirk class, found by execution, that the original inventory did not
  distinguish from the 37 "nested object without `additionalProperties`" tools**: a nested
  field that is a **bare free-form dict** — the literal schema is exactly
  `{"type": "object"}` with **no** `properties` key and no `additionalProperties` key at
  all (e.g. `commitments.installments`/`funding_plan`/`actions`, several `changes`/`input`/
  `params` bags across `code.py`/`skills.py`/`scheduling.py`/`portfolio.py`/`profile.py`).
  This is NOT the same shape as a nested Pydantic model (which the existing non-`forbid`
  nested base from Phase 3 handles): a plain `Dict[str, Any]` field always emits
  `additionalProperties: true` (verified directly — see the field's own JSON schema), which
  is a byte-for-byte mismatch against a literal that omits the key altogether, not a
  cosmetic difference the canonical-JSON comparison shrugs off. None of `Dict[str, Any]`,
  bare `dict`, or bare `list` produced a match; every one of these was left as a literal
  rather than migrated with a guessed workaround. **Fixing this needs its own opt-in
  helper** (mirroring `explicit_null`'s pattern — a `json_schema_extra` callable that pops
  the auto-added `additionalProperties` key) before this sub-bucket can be migrated
  mechanically; until then, treat any nested field reported as "missing
  `additionalProperties`" with **no** `properties` key as its own case, not Phase 3's.

**A second technique, found by necessity, not anticipated by the ADR:** several tools'
literal declares an OPTIONAL scalar-or-list field (`anyOf: [string, array]`) with **no** `null`
branch at all (`update_price_alerts.alert_ids`, `set_news_sources_enabled.source_ids`,
`remove_watchlist_items.item_ids`, `update_watchlist_items.item_ids`, `get_payees.payee_ids`,
`set_payees_hidden.payee_ids`, `set_payees_autocategorize.payee_ids`,
`remove_payee_rules.payee_ids`, `set_payees_rules.payee_ids`, `delete_payees.payee_ids`, and
`delete_watchlists.watchlist_ids`) — genuinely optional (absent from the tool's own
`required` list) but never spelled with the third `null` branch `Optional[Union[str,
List[str]]]` would emit (and that transform 2 can't collapse — it only fires on the exact
2-branch X-or-null shape). Fix: annotate the field as the BARE `Union[str, List[str]]` (no
`None` in the type) but set `default=None` at the `Field(...)` level — Pydantic does not
validate a default against its annotated type unless `validate_default=True` (off by
default), so the JSON schema reflects only the annotated 2-branch union while the field is
still excluded from `required` because it has a default. Safe here specifically because these
`ToolInput` models are schema factories ONLY — never instantiated against real tool-call data
(dispatch validates the raw dict directly) — so the type/default mismatch is inert. Documented
at each use site with a one-line comment pointing back to the first occurrence
(`alerts.py`'s `update_price_alerts`).
