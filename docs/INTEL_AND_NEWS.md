# Intel — the Analyst pipeline and news ingestion

> **On-demand reference.** Not loaded into every turn — read it when you touch this area.
> Decisions and their reasoning live in [`docs/adr/`](adr/); this file states current truth.

**`pending_analysis`** — the Analyst event ledger (`PendingAnalysisStore`, a DB table, checkpoint-EXCLUDED — runtime scheduler state, mirrors `batch_ledger`). The **Intel Analyst** pipeline (RFC `.claude/rfcs/lucius-wealth-manager-and-analyst.md`): **Phase 1** (`monitoring/crash_watch.py` + `price_monitor._run_crash_lane`) fires a deterministic crash signal on any holding cratering past `services/watchlist.CRASH_MOVE_PCT` (equity 12 / commodity 15 / crypto 25; cash/property/bond off) and **enqueues** a pending-analysis row. **Explicit price alerts are news-aware (INT13, owner incident 2026-07-16 — an ONWAI alert narrated a "technical breakout" thesis 30 min after this same system had already analyzed and pushed the rival's acquisition-offer news driving the move):** `price_monitor._news_context_for_alert` injects the asset's current intel signal (checked across the `news-{instrument_id}` and `crash-watch-{ticker}` id families, freshest wins) as a `prior_analysis_block`-fenced PRIOR NOTE plus up to 4 fresh (<=24h) evidence headlines fenced/sanitized via `analyst_prompt.render_news_context_block` (reusing the INT12 machinery, not a parallel convention) into the SAME single `_ai_signal` narration call — instructing the model to interpret the move in light of a known event instead of framing it as generic technical momentum; the evidence read is off-loop (`asyncio.to_thread`) and the whole block is a graceful no-op (prompt byte-identical to before) when there's no signal/evidence. **Phase 2** (`monitoring/analyst.run_analysis_sweep`, a ~60s `analysis_sweep` scheduler job) drains the ledger with an atomic `claim()` (overlap-safe), gathers cached evidence + a free guarded on-move RSS freshen, runs ONE bounded LLM synthesis via `core.llm_seam.complete` (the "why" + impact + actions — no agent tool-loop, no paid web search), updates the in-app crash signal, and pushes the analyzed follow-up FAIL-CLOSED to configured `notify_routes.news` only (never `in_app`). **The external push is MATERIALITY-GATED (INT14a, owner incident 2026-07-16→18 — 41% of 130 sent alerts were exactly-verbatim "nothing material has changed" rehashes; compounded by a 13h-median drain backlog surfacing stale triggers as 3am pushes):** the synthesis prompt (`analyst._build_prompts`) now requires a structured `{"materiality": "new|update|no_change|awaiting_detail", ...}` JSON field alongside why/impact/actions — the model's OWN verdict on whether THIS alert differs from the prior note; `analyst._materiality_of` reads it defensively (missing/unparseable/out-of-vocabulary → `"update"`, fail toward informing rather than silence — only an EXPLICIT value ever suppresses). `analyst._push_decision` gates the external push on TWO suppression conditions, checked materiality-branch-first (not independent — a stale row whose materiality is ALSO `no_change`/`awaiting_detail` reports under the materiality reason, never "stale"; the in-app signal upsert is unconditional either way, so the Intel feed/timeline always stays current): (1) `materiality in ("no_change", "awaiting_detail")` — `no_change` is Part A's original no-op-rehash case; `awaiting_detail` (INT16, owner incident 2026-07-18 — an NVDA "Announces Q4 Results" headline pushed with zero figures) is a GENUINELY NEW event that is content-thin, an announcement/headline with no substantive figures/terms/price-reaction/confirmed-details yet to act on — distinguished in the prompt from `"new"`, which requires the first coverage to already carry real substance, and from `"update"`, which requires a genuine new fact beyond a prior note; the prompt EXPLICITLY guards the dangerous false-suppression direction — a CONFIRMED QUALITATIVE development (a resignation, an investigation opened, a ruling, a recall, an outage, a confirmed personnel/strategic change) is substantive on its own even with no dollar figure attached, so it's `"new"`/`"update"`, NEVER `"awaiting_detail"` — `awaiting_detail` is reserved for an actual placeholder announcement whose real content hasn't landed yet, never "no numbers were mentioned." Suppressed the SAME way as `no_change` but under its OWN log reason, and NOT a permanent silence — the follow-up coverage that supplies the actual figures diffs against this row's own thin summary via the INT12 prior-note mechanism and lands on `"update"`, which pushes normally, so the gate is a one-tick delay. (2) — only reached when materiality is `new`/`update` — the row is STALE — `analyst._row_age_hours` vs. `_STALE_PUSH_HOURS` (6h) measured off the row's OWN `created_at` (enqueue time, never the headline's own date), so a backlog-drained trigger analyzes and updates its signal but never fires a late "breaking" push. Each suppression logs at INFO (`"analyst: suppressed no-change push for %s"` / `"analyst: suppressed awaiting-detail push for %s"` / `"analyst: suppressed stale push (...)"`) so it's observable, never silent. The drain-throughput backlog itself is fixed separately by INT14b (below), not in scope for INT14a itself. **The in-app TIMELINE is separately materiality-gated too (INT15, owner-reported bug — the timeline was accumulating a meaningless "Analysis" row on every sweep tick even after INT14a silenced the push):** `analyst._update_signal` appends a timeline row only on `new`/`update` (titled with the materiality label — "New development"/"Update" — never the old hardcoded "Analysis"; `summary` carries the real "why"), never on `no_change`. Storage is UNBOUNDED (F11 fix, owner-reported 2026-08-29 — the original hard `_TIMELINE_CAP` (20) truncation silently evicted real months-old pushed-alert history, an unacceptable "never silently degrade/discard data" violation; removed entirely). Only READS are bounded now: `GET /api/intel/signals` embeds each signal's most-recent 20 (`showing_timeline`/`total_timeline` reported) with `GET /api/intel/signals/{id}` as the full-history fetch (`services/intel_signals.py`), and `get_asset_context`'s own pre-existing `timeline_limit` was already correct against an unbounded source. **Shorter alerts + portfolio_impact replace-not-append (INT18, owner incident 2026-07-19 — two SEPARATE problems):** (bug) `analyst._update_signal` used to APPEND each re-analysis's reworded impact onto the signal's stored `portfolio_impact` (the `not in` substring dedup only caught a byte-identical repeat, never a paraphrase) — a long-lived signal's IN-APP impact field grew to 8-20 concatenated near-duplicate variants (one real book: ~5,200 chars of "0.4% of net worth, this is noise" reworded over and over). Fixed to REPLACE: `portfolio_impact = impact_note or (prior portfolio_impact)` — the CURRENT analysis's impact IS the impact, the timeline already carries the history of what changed; a fresh EMPTY impact (e.g. a `no_change` tick) keeps the prior rather than blanking the signal. (quality) the PUSHED Telegram message separately ran 1,000-1,300 chars — a hedged `impact` paragraph rendered even when the news was immaterial noise to the position, plus a multi-clause action bullet. `_build_prompts`' system+user prompt AND `_AnalysisOutput`'s field `description`s (the derived schema's per-field descriptions ride into the structured-output prompt too — a second, redundant channel) now instruct brevity: `why` ≤ two tight sentences; `impact` is ONE sentence and OMITTED ENTIRELY (empty string) when the news is immaterial/noise relative to the position size, instead of a paragraph explaining why it doesn't matter; `actions` is AT MOST ONE terse imperative, never a run-on sentence. Enforced defensively in code too — the `[:5]` action-list truncation in `analyst._update_signal`/`_create_news_spike_signal` and `topic_analyst.create_topic_spike_signal` is now `[:1]`, and `analyst._format_analysis` (the push renderer) emits only the first action and applies a hard `_ALERT_MAX_CHARS` (800) cap via `_truncate_at_sentence_boundary` (cuts at the last sentence-ending punctuation in range, never mid-word) as a belt-and-suspenders backstop against a model that ignores the prompt guidance — target alert length ~400-600 chars, down from 1,000-1,300. **The external push is also DECISION-RELEVANCE-GATED (INT19, owner-diagnosed 2026-08-25 — a live-data audit of a real 26h/35-push window):** materiality alone answers "is this a fact I haven't told you before" (novelty), not "does this change what you'd do" (decision-relevance) — a deeper audit of the SAME window's live signals found 24 of 31 resolved to a generic `Hold`/`No action needed` `action_items` entry with the model's own `portfolio_impact` text saying "barely moves the needle"/"immaterial"/"changes nothing meaningful", yet still pushed, because a technically-novel-but-mechanical event (a passive index inclusion, a routine/tiny insider sale, a financing round closing with terms already known) passes materiality's `new`/`update` bar exactly like a real catalyst does. The synthesis call now also returns a structured `decision_relevant: bool` (`_AnalysisOutput`, read defensively by `analyst._decision_relevant_of` — missing/non-boolean → `True`, same fail-toward-informing default as `_materiality_of`); `analyst._push_decision` adds it as a THIRD suppression condition, checked model-verdict-first alongside materiality and before the mechanical staleness check (own log reason `"analyst: suppressed immaterial-impact push for %s"`). The prompt (`analyst._build_prompts`'s three worked examples) instructs `False` ONLY when the model's OWN impact conclusion is genuinely negligible for the position size or the event is passive/mechanical; `True` for everything else, INCLUDING a thesis-confirming `Hold` on a real earnings beat/miss or price move — `decision_relevant` is explicitly NOT "the action is something other than Hold". Deliberately NOT a position-size floor: an earlier design (suppress by % of net worth) was owner-rejected — whatever a user chooses to monitor should still surface a genuinely actionable/thesis-relevant development regardless of position size; only a development the model's own analysis concludes is a non-event is suppressed, so a small, closely-watched position (e.g. a speculative starter stake) still gets its genuinely material alerts. `decision_relevant=False` suppresses ONLY the external push, exactly like `no_change`/`awaiting_detail` — `_update_signal`'s in-app TIMELINE gate is unchanged (keyed on `materiality` alone), so a subject's own Intel feed still shows every genuinely new development even when its push was withheld. **Zero-delivery push retry (INT6, 2026-07-16 incident — a hot-reload-mid-reconnect Telegram push returned `{"sent": 0}` and was silently treated as success):** every push logs its delivered dict at INFO; if EVERY channel reports zero delivery, the rendered message is queued in `PendingPushStore` (the `pending_pushes` DB table, checkpoint-EXCLUDED) and retried with bounded backoff (60s/300s/900s, 3 attempts) by `monitoring/push_retry.py`'s `drain_pending_pushes`, called at the top of every `run_analysis_sweep` tick regardless of pending analyses — a durable queue survives a process restart/hot-reload, unlike an in-memory asyncio timer. Shared by both external-push call sites (`analyst._push_analysis` and `price_monitor._push_external_alert`); a recovered retry logs INFO once, exhausted retries log ONE WARNING. **Per-subject coalescing + watermarked evidence + cluster-dedup (INT14b, owner-diagnosed backlog 2026-07-18 — a single hot subject spawned one pending row PER TRIGGER, e.g. 230 news_spike + 107 material_news rows for one ONWAI-acquisition story, each re-reading the same freshest-8 headlines and producing a near-identical analysis; drained at the old `_DAILY_ANALYSIS_CAP=50/day` → a 13h-late, ever-growing backlog):** `PendingAnalysisStore.upsert_pending` (the enqueue choke EVERY producer — `crash_watch`/`price_monitor`'s crash lane, `rss_poller`/`rss_poller_topics`'s news_spike, `news_screen._enqueue_material`'s material_news — now routes through, replacing bare `add()`) MERGES a trigger into an existing UNCLAIMED `pending` row for the same subject instead of always appending a new one; a `claimed`/`done` row is left alone, so the next trigger after an in-flight/completed analysis opens a fresh row (the subject is "hot again"). On merge: `created_at` stays the EARLIEST arrival (the INT14a staleness guard keeps measuring true wait time); `trigger`/payload go "material_news"-STICKY (once any merge carries a material_news trigger — the only kind with an actual headline — the row's `trigger` becomes/stays "material_news", keeping analyst.py's `>>> NEW` marker check working unmodified) and a later material_news merge overwrites the marker fields (headline/published_at/cluster_tokens) with its own, so the analysis leads with the freshest real development; each material_news merge also appends its own `{at, cluster_tokens}` onto `payload.material_events`, which `PendingAnalysisStore.recent_material_events` (replacing `recent_rows`) reads instead of counting rows — this is what keeps `news_screen`'s INT12 subject-floor/fingerprint cooldown correct under coalescing (several distinct screen events can now live on ONE coalesced row; counting rows would silently undercount the floor). `_process_row`'s evidence read is now a per-subject WATERMARK, not a blind freshest-8 slice: a DEDICATED signal field, `evidence_watermark` (None on a first-ever/bootstrap analysis, which keeps the old freshest-8 behavior; deliberately NOT `updated_at`, which keeps its original "when this signal's synthesis last completed" meaning) bounds `services.evidence.read_evidence`'s new `since` param (filters to `first_seen` — the cache-arrival time — strictly newer than the watermark) — "everything that arrived since we last looked," capped at `_WATERMARKED_READ_LIMIT` (200 rows — bounded, not unbounded). `monitoring/analyst_prompt.collapse_to_distinct_stories` (built on a new shared `cluster_by_content_overlap`, the SAME token-overlap algorithm `news_screen._cluster_rows` already used, now with ONE implementation instead of two copies) then collapses that read to at most `_MAX_DISTINCT_STORIES` (8) DISTINCT clusters, newest representative each, BEFORE the existing INT12 trigger-marker/newest-first/>24h-cap layer runs on the smaller deduped set — so a syndication flood of near-duplicate copies can't crowd out 2-3 genuinely different developments; recency for cluster ordering/representative-selection is CLAMPED (`analyst_prompt._clamped_recency_hours` = `max(recency(published_at), recency(first_seen))`) so a feed-controlled future `published_at` can't pin an attacker's copy as the kept representative or sort it ahead of legitimate items. `analyst._read_and_collapse_evidence` runs the read AND the clustering TOGETHER inside ONE `asyncio.to_thread` offload (security fix — clustering is O(n²) over the read's size and must never run synchronously on the event loop). `_PER_SWEEP_CAP`/`_DAILY_ANALYSIS_CAP` are now a loose RUNAWAY SAFETY NET (10/tick, 500/day — raised from 5/50), not an operating rate control: coalescing keeps the queue small, pushes are already materiality-gated (INT14a), and real per-analysis cost is ~$0.0012, so the old cap was starving a normal-rate queue for negligible savings. `payload.material_events` (above) is capped at `_MAX_MATERIAL_EVENTS` (20, most-recent-first) so a never-drained row can't grow it unboundedly. One-time transient (not a data migration): rows enqueued before this change won't retro-coalesce, but drain fast under the raised cap and are mostly suppressed by INT14a's materiality/staleness gates regardless. ADR: `docs/adr/2026-07-18-per-subject-analysis-coalescing.md` (includes a post-QA-gate Security hardening section covering all four fixes above plus the evidence-arrival race: `evidence_watermark` is stamped from the READ-time captured before the evidence read, not the LLM-completion time, so evidence landing mid-call isn't silently lost forever). Budget caps: per-run `max_tokens` + the rolling-24h `_DAILY_ANALYSIS_CAP`. Evidence is treated as UNTRUSTED (control-char strip, dash-collapse to block delimiter-escape, length caps, an explicit untrusted-data system guard); errors log `type(exc).__name__` only. **Phase 3** (ADR 0006): a tiered fast RSS poller (`monitoring/rss_poller.run_rss_poll`, `rss_poll_fast`/`rss_poll_slow` jobs) fills the evidence cache with NO LLM; a **publish-based** news-spike detector (counts `published_at`, ≥ floor AND ≥3× the subject's own baseline, cold-start-guarded, per-tier capped — NOT fetch-count, see the ADR 0006 incident) enqueues a `news_spike` event into the same ledger/sweep. The spike math itself lives in `monitoring/spike_detection.py` (subject-agnostic — takes plain evidence rows, doesn't know asset vs. topic) shared by BOTH the fast tier (top-25 held assets, subject `asset:{instrument_id}`) and, since INT3, watchlist topics (subject `topic:{item_id}`, gated on the item's own `monitor_news`, its own independent `_SPIKE_MAX_PER_POLL` counter so a busy topic news day can never crowd out an asset spike or vice versa; the 90-min `_SPIKE_WINDOW_SEC` is reused unchanged since it's rate-based, not count-based, and comfortably spans the slow tier's ~30-min cadence) — **since INT7, `monitor_news` topics ALSO get the fast tier's cadence** (up to `_TOPIC_FAST_CAP` per tick; the rest still wait for the slow tier, which keeps polling every topic regardless, cache-TTL-deduped and cooldown-guarded against a cross-tier double-enqueue), closing a measured gap where a watched topic's own feeds lagged held assets by up to ~25 min of avoidable poll cadence. Topic feed processing (shared by both tiers) lives in `monitoring/rss_poller_topics.py` (split out of `rss_poller.py` to stay under the file-size convention, mirroring the `rss_poller_hot.py` precedent). `monitoring/analyst.py`'s sweep handles both row shapes through one pipeline — a topic row has no instrument/ticker to enrich with, so it uses `monitoring/topic_analyst.py` (RSS freshen via `resolve_topic_feeds`, the watchlist item's own note as context instead of a position, and creates/updates a `type="topic"` signal) instead of the asset-specific position/RSS helpers; `monitoring/text_sanitize.py` holds the shared untrusted-text sanitizer both paths use for prompt content. Opportunity discovery is FREE by default (RSS discovery queries + Yahoo screener `prices.fetch_movers`; paid web search opt-in via `web_search_enabled`; in-app only). A scheduled digest (`monitoring/digest.py`, `eod_digest`/`premarket_digest` cron jobs; `digest_state.json` once-per-day marker, checkpoint-EXCLUDED) delivers an end-of-session rundown + conditional pre-market brief — one bounded narration call, channel-agnostic single message.

**Timeline entries are sourced and a reversal needs corroboration (ADR `2026-08-28-sourced-and-corroborated-intel-signal-updates`, owner incident 2026-08-25 — an ONWAI signal pushed "the rival's takeover bid was rejected" to Telegram as confirmed fact, with NO source, directly contradicting a "formal takeover agreement confirmed" entry from 4 days earlier; a sweep of 25 real signals found 24 had zero recorded sources on their latest update — corrected the SAME day by a security review that actually RAN the code against crafted inputs, see the ADR's own Correction section):** every timeline entry `analyst._update_signal`/`_create_news_spike_signal`/`topic_analyst.create_topic_spike_signal` inserts carries a stable `id` (`uuid4().hex`) and `sources` (`[{url, title, domain}]`, each field sanitized via `sanitize_untrusted_text`, capped at 3 sources with a 300-char stored URL cap — built from the SAME evidence list the synthesis call read — `analyst_prompt.source_dicts`, sharing its qualifying-evidence filter with `_source_links` via `iter_valid_sources` so the two can never disagree on which evidence counts). The synthesis call is also shown its own subject's recent timeline entries (id + date + summary, capped at 5, newest-first, with an explicit `[UNCONFIRMED]`/`[SUPERSEDED]` marker on any entry that isn't a plain confirmed note — `analyst_prompt.prior_notes_block`, fenced as `--- BEGIN/END YOUR PRIOR NOTES ---`, the same recycled-model-output-is-DATA-not-instruction treatment as the single-summary `PRIOR NOTE` block) and returns three new structured fields alongside `materiality`/`decision_relevant`: `source_url` (**informational only** — the evidence block shown to the model never contains a URL, so nothing gates on this field; it's cross-checked against the real evidence, `analyst._verified_source_url`, before being surfaced anywhere), `duplicate_of_id` (a semantic judgment — this restates a specific prior note with nothing new), and `contradicts_id` (this reverses a specific prior note) — both id fields get `decision_relevant`'s same defensive `mode="before"` coercion (a hallucinated non-string id never fails the whole response) and are resolved against the signal's own timeline by `analyst._find_timeline_entry`, where an unmatched/hallucinated id is treated as no reference at all, never as a reason to drop a genuinely new development. A matched `duplicate_of_id` is refused outright when `materiality == "new"` (self-contradictory) or when `why` has no real content-overlap with the referenced entry's own summary (`analyst._texts_overlap`) — otherwise it short-circuits everything: no new timeline row, only the matched entry's `as_of` refreshes, `evidence_watermark` does NOT advance (a wrongly-suppressed development stays eligible to be re-read next tick), and the suppression is logged with the referenced id AND the discarded `why` (`"analyst: suppressed duplicate-of-prior-note push for %s (id=%s, why=%.200s)"`). A matched `contradicts_id` computes corroboration via `analyst._independent_source_count`: evidence is first filtered to items that actually overlap the claim text (`analyst._claim_relevant_evidence`, reusing `content_tokens` — the same primitive `is_same_story`/`cluster_by_content_overlap` are built on), then counted by DISTINCT REGISTRABLE DOMAIN (`core.urls.registrable_domain`), never raw `core.news.dedupe_stories` cluster count (same-publisher-only, no relevance check — proven exploitable by the security review); counted against a LESS-collapsed evidence read (`_process_row`'s `raw_evidence`) than the prompt itself sees, since the prompt-facing collapse is publisher-agnostic and would otherwise merge genuine multi-outlet corroboration away before it could be counted. ≥2 independent, claim-relevant sources CONFIRMS the reversal (the new entry gets `supersedes`/`confirmed_at` — anchored on the freshest SUPPORTING evidence item's own clamp-protected timestamp, `analyst._freshest_supporting_timestamp`, never the wall-clock write time — and the old entry is superseded via a copy, never mutated in place); fewer holds it `flagged`/`contradicts` — visible in-app, never pushed, and never re-evaluated on a later pass (corroboration is same-synthesis-call only in this slice — see the ADR). `analyst._push_decision` gains a GROUNDED gate, evaluated after decision_relevant and before staleness: an entry with an EMPTY `sources` list, or a `flagged` status, suppresses under the dedicated reason `"ungrounded"` (a missing `entry_meta` fails CLOSED here, unlike every other gate in this file); a structural non-case (a crash-trigger row whose signal was deleted between enqueue and drain) gets its own distinct `"signal_missing"` reason, never confused with a genuine grounding failure. For a confirmed-late reversal, the staleness check measures age from the entry's own `confirmed_at`, not the pending row's `created_at` — per-subject coalescing (`PendingAnalysisStore.upsert_pending`) pins `created_at` to the EARLIEST arrival, so a reversal that legitimately took a day to corroborate would otherwise age out of the 6h push window before it could ever fire. No new store/table — this is an in-place extension of the existing `intel_signals` JSON row shape.

**Low-latency news ingestion (INT5, `.claude/rfcs/news-ingestion-latency.md`)** — driven by a measured incident (Jul-14 ONWAI-acquisition: 4.3h alert lag; topic feeds were Google-search-RSS-only, median 3.4h publish→cache). **Arrival is now a first-class event**: `core/news_arrivals.py` (a leaf registry, `core.channels`'s pattern) lets `monitoring` register CONSUMERS that react to newly-inserted evidence rows; `monitoring.collect.gather_rss`/`gather_matched` `emit()` a row the FIRST time its `seen_count` becomes 1 (dedup-merge already tells you this — no separate before/after diff needed), one consumer's exception isolated so it never sinks a poll. A third poll tier, **hot** (`monitoring/rss_poller_hot.py`, scheduler job `rss_poll_hot`, ~90s, same `news_freshness` on/off gate as `rss_poll_fast`), covers near-real-time sources the 5/30-min tiers are too slow for: a **per-market regulatory-disclosure REGISTRY** (`services/feeds_regulatory.py` — a table keyed by the Yahoo-ticker exchange suffix, reusing `feeds._SUFFIX_LOCALE`'s convention; v1 ships DE/CH/AT → the finanznachrichten.de EQS ad-hoc mirror, else → SEC EDGAR's current-8-K Atom feed with its own declared `EDGAR_USER_AGENT` — SEC fair-use requires one or requests are dropped; adding a market is one registry entry, no poller change); **ONE combined GDELT query per tick covering every `monitor_news` topic** (`services/feeds_hot.py` — GDELT's rate limiter bans an IP after ~2 calls, verified live, so a per-topic fan-out is unsafe); and per-item **`custom_feed_urls`** (owner directive, open-source generalization — any watchlist ticker/topic can point up to 5 of its own feed URLs, http(s)-only, SSRF-guarded at the `WatchlistStore` write choke covering REST + every AI-tool write in one place). A shared firehose/query fans its hits out to every entity it matches via `services.feeds_hot.match_hits_to_subjects` (case-insensitive name/ticker-token substring match, no LLM) — `monitoring.collect.gather_matched` is the collector shape for this (vs. `gather_rss`'s one-feed-one-subjects-list model). Watchlist topics gain optional `linked_tickers` (`services.feeds.resolve_topic_feeds`) so a topic ALSO rides its linked ticker's fast Yahoo lane instead of only the (now `when:1d`-suffixed, `cadence: slow`) Google search RSS. **Per-source latency observability**: `services/news_latency.py: lag_stats(days=7)` (per-`via` `{n, median_hours, p75_hours}`, reusing `services.evidence`'s tolerant timestamp parser) → `GET /api/intel/source-latency` + AI tool `get_news_latency` (a read; `core.agent_caps._T0` / `HEADLESS_ALLOWED_TOOLS` and the sync requirement between them are GONE as of 2026-07-18). `_fetch_feed` (monitoring/collect.py) gained conditional-GET support (ETag/Last-Modified round-trip, a 304 keeps the prior cached hits) and an optional `user_agent`/`parser` override for non-default sources. **Phase 2 (consumers)**: `monitoring/news_screen.py` is a `core.news_arrivals` CONSUMER — THE volume-independent fast path (one material headline is enough, no count threshold): filters arrivals to `monitor_news`-watched subjects, clusters same-subject headlines by normalized-title token overlap (no LLM), and for each not-recently-screened cluster runs ONE batched LLM call (task `news_screen`, added to `model_config_store.VALID_TASKS` + REST-settable via `PUT /api/model-config/task-models`) returning per-cluster `material: bool`; a material verdict enqueues `PendingAnalysisStore(trigger="material_news")` — capped per-tick (`_MAX_CLUSTERS_PER_TICK`), a rolling calendar-day budget (`news_screen_state.json`, digest.py's state-marker pattern), and a 6h dedup window that is CLUSTER-AWARE, not subject-blanket (INT12, fixed after a live incident: the old blanket per-subject cooldown suppressed a genuinely new follow-on development — a stake-sale/bid headline on a subject already screened that window — as if it were a re-syndicated copy): a candidate cluster's own token fingerprint (`cluster_tokens`, persisted on the row's payload) is compared against every material_news screen EVENT enqueued for that subject within the window (`PendingAnalysisStore.recent_material_events` — renamed/generalized by INT14b's per-subject coalescing to flatten `payload.material_events` across rows rather than count rows, since several distinct events can now live on ONE coalesced pending row) — a fuzzy match (the same `_CLUSTER_OVERLAP` threshold `_cluster_rows` clusters with) suppresses a re-syndicated copy, a miss lets a genuinely distinct cluster through, bounded by a subject-level floor (`_SUBJECT_SCREEN_FLOOR`, 3 distinct clusters per window before falling back to a blanket cooldown) against cluster-splitting spam; NO-OPs cleanly (never raises) when the LLM seam is unavailable. `monitoring/analyst.py` treats `material_news` as a THIRD trigger sharing the SAME `news-{iid}`/`news-topic-{item_id}` signal-id family as `news_spike` (so it updates/creates the one signal per subject regardless of which trigger fired) — its own event framing ("a material headline just arrived") never quotes the raw (untrusted) headline in the unfenced part of the prompt, only inside the existing delimited evidence block, where (INT12) it is now MARKED distinctly (`>>> NEW (this alert's trigger, published <ts>):`, a code-rendered marker collision-proofed the same way the block delimiters are — `text_sanitize.py`'s `>`-run collapse, NFKC-normalized FIRST so a fullwidth lookalike can't smuggle a run past the collapse) so the model can identify and lead with the actual trigger instead of treating it as indistinguishable background;
